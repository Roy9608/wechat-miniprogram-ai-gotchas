# 04 · 批量改码陷阱

跟小程序无关，但它是「AI 帮你改存量代码」这个动作本身的失败模式。

单独开一类的原因：这一类坑不产生报错、不产生异常，产生的是**一份看起来改好了的、错的代码**。而且通常发生在批量操作里——一次改几十处，你不可能逐处核对。

## 待收录

| 状态 | 现象 |
|---|---|
| ☐ | 正则批量替换误伤结构相似的其他字段（引用数组被当成数据行） |
| ☐ | 批量替换把「说明这条规则的文字本身」也改了 |
| ☐ | 提取脚本的编号正则写死位数，超过位数的条目静默丢失 |
| ☐ | 文档里描述的字段形态 ≠ 数据实际形态，按文档写导致功能全失效 |
| ☐ | 测试断言随数据更新而过期，要区分「断言旧了」还是「数据错了」 |
| ☐ | 批量转换把列表符号残留在正文里 |
| ☐ | 跨工具写入导致换行符混用（CRLF / LF） |

## 通法

这一类里绝大多数事故，都能被同一个动作挡住：

> **先枚举全部命中，人工过一遍，再动手。**

跳过"枚举"直接替换，就是在赌"我想到的模式和实际存在的模式完全一致"。真实项目里这个赌注几乎必输——尤其是当你要替换的东西是短字符串（一个数字、一个词、一个符号）的时候，它在别的语境里出现的概率远高于你的直觉。

第二个通法：

> **改完必须能验证「没有改多」。**

只验证"目标改对了"是不够的，还要验证"非目标没被改动"。做法是先 diff，逐段确认每一处改动都是想要的——这在批量操作里是必须步骤，不是可选步骤。
