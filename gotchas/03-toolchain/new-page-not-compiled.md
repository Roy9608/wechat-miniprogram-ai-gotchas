# 新增页面后报 xxx.wxml not found，其实不是路径错

- **分类**：工具链
- **触发概率**：中。新建页面目录后偶发
- **危险等级**：功能没上线，但真正的风险是**AI 会为此改一堆本来正确的代码**

## 症状

新增一个页面，按标准流程做了：

- 建了 `pages/foo/foo.wxml` / `.js` / `.wxss` / `.json`
- 在 `app.json` 的 `pages` 数组里注册了 `pages/foo/foo`
- 路径逐字符核对过，大小写一致

编译，跳转时报：

```
pages/foo/foo.wxml not found
```

最迷惑的是：**首页新加的入口卡片是生效的**（说明 `app.json` 的改动被吃进去了），但点进去就报找不到文件。

## AI 的错误反应（这才是真正要防的）

这是为什么这条要收进库里——**错误本身不贵，AI 对错误的反应很贵**。

看到 `not found`，AI 的第一反应是"路径写错了"，然后开始一连串修改：

1. 把 `app.json` 里的 `pages/foo/foo` 改一次（可能是无意义的等价改写）
2. 把文件名改成别的
3. 怀疑大小写，改一遍
4. 怀疑 `app.json` 的 `pages` 顺序有影响，调整顺序
5. 怀疑要补 `foo.json` 里的 `usingComponents`，加上去
6. 还不行，干脆把整个页面删掉重建一遍

**每一步都在往一个正确的项目里注入新的不确定性。** 原本只是一个缓存问题，最后变成"页面重建过、配置改过、顺序调过"，即使后来能跑了，你也说不清是哪一步好的，下次复现不了。

而且：如果这个页面里已经有写完的业务逻辑，删掉重建 = 逻辑重写。

## 为什么会出现

`not found` 只说明「运行时没找到这个文件」，不等于「磁盘上没有这个文件」。

两者之间隔着一整条链路：

```
磁盘文件 → 开发者工具的文件监听 → 增量编译产物 → 运行时加载
```

这条链路上任何一环没跟上，表现都长成一模一样。常见原因：

- **增量编译没收录新目录**：新建的目录没有触发文件监听，编译产物里根本没有它。这是最符合「新入口生效、新页面找不到」这个组合的原因
- **`miniprogramRoot` 指错**：开发者工具实际编译的不是你以为的那个目录
- **多个 project 配置文件打架**：项目里有不止一份 `project.config.json` / `project.private.config.json`，工具读的是另一份
- **文件带隐藏字符或 BOM**：路径里混进了不可见字符

这四种里，只有第 3、4 种是"真的有问题"，前两种是"代码没问题，环境没同步"。

## 排查顺序：从最便宜的做起

**在动任何代码之前**，按这个顺序查。每步都能给出确定结论，不要跳着猜。

### 第 1 步：证明文件真的存在

```bash
ls -l pages/foo/
```

看四个文件是否都在、大小是否正常、文件名大小写是否和 `app.json` 里完全一致。

如果文件不在 → 这是真的缺文件，去建。到此为止。

### 第 2 步：逐字符对比路径

```bash
grep -n "foo" app.json
```

把 `app.json` 里的字符串和磁盘上的文件名并排放，一个字符一个字符看。特别看：

- 有没有多余空格
- 大小写（`Foo` vs `foo`）
- 全角字符混进路径（复制粘贴时的常见事故）

### 第 3 步：确认工具在编译哪个目录

```bash
cat project.config.json | grep -i "miniprogramRoot"
ls project.*.config.json
```

检查两件事：

- `miniprogramRoot` 如果存在，值是不是指向包含 `app.json` 的那一层
- 有没有第二份 `project.private.config.json`，它的配置会不会覆盖前面的

**常见的坑是 `miniprogramRoot` 指到了外层。** 这时候工具编译的是外层的 `app.json`（可能是个残缺的旧版本），你在里层加多少页面都没用。

### 第 4 步：查隐藏字符和 BOM

```bash
file pages/foo/foo.wxml
xxd pages/foo/foo.wxml | head -1
```

开头如果是 `ef bb bf`，就是带 BOM 了。部分环境下列器不认这个。

### 第 5 步：只有前四步都过了，才清缓存

到这一步才能判定是编译产物没跟上。动作：

1. 开发者工具 → 清缓存 → **全部清除**
2. 重新编译
3. 如果还不行，删掉编译产物目录（`miniprogram_npm` 之外的那个临时输出目录），重开项目

**为什么清缓存放最后**：它是"重来一次"，不提供任何诊断信息。你先清了缓存、问题消失了，你永远不知道原来是什么原因，下次遇到还得重新试一遍。而前面四步无论结果如何，都能给你一个确切答案。

## AI 该怎么被约束

给 AI 下指令时，加一句就能挡掉大半瞎改：

> 报 `not found` 时，先只做只读排查（文件是否存在、路径是否逐字符一致、`miniprogramRoot` 指向哪），**不要修改任何文件**，把排查结果告诉我再决定。

原因是 AI 的默认倾向是"遇到错误就修改"，而这类错误的正确反应是"先证明哪一环断了"。

## 怎么验证修好了

不要用「点进去不报错了」当验证标准，因为清缓存可能只是让你这一次不报错。

验证方式：

1. 关掉开发者工具，重开项目，再点一次
2. 真机预览点一次（真机走的是完全不同的加载路径）
3. 如果涉及新目录，再新建一个空页面测一次，确认工具能正常收录新目录

第 3 步是关键：**如果新建目录仍然不被收录，说明不是缓存问题，是文件监听坏了**，得重装或换版本。
