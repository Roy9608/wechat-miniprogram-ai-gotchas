# WXML 绑了 bindtap，JS 里没这个方法，点了没动静

- **分类**：静默失败
- **触发概率**：高。AI 分两次生成 WXML 和 JS 时几乎必出
- **危险等级**：功能完全失效，编译阶段不报任何错

## 症状

页面上有个按钮，点了什么都不发生。

控制台通常会提示找不到处理该事件的方法（不同基础库版本的提示文案不完全一致，有时会被折叠在 Filter 之外的输出里，容易漏看）。但**编译是通过的**，`app.json` 也正常，文件也都在。

更麻烦的是它经常不是「整个页面挂掉」，而是「只有这一个按钮挂掉」——其它交互都正常，所以第一反应往往是"是不是这里被别的元素挡住了"，然后去排查层级、定位、`z-index`，全查完发现没问题。

## AI 的默认写法

没有一个"错误代码"可看，因为错误是**缺失**，不是写法。

典型成因有三种，都跟 AI 的工作方式直接相关：

**第一种：分两次生成**

```html
<!-- 第一轮：生成 WXML -->
<view class="search-bar">
  <input bindinput="onSearchInput" value="{{keyword}}" />
  <view class="clear" bindtap="onClear">✕</view>
</view>
```

```js
// 第二轮：生成 JS —— 漏了 onClear
Page({
  data: { keyword: '', list: [] },
  onSearchInput(e) {
    this.setData({ keyword: e.detail.value });
  }
  // onClear 没写
});
```

**第二种：改名只改了一边。** 迭代中把 `doSearch` 改成 `handleSearch`，改了 WXML 忘了改 JS，或者反过来。

**第三种：删方法时没清理绑定。** 重构时把某个处理函数删掉了，WXML 里的 `bindtap` 留着。

三种的共同点：**AI 认为这两份文件是一起改的，但实际生成是分开的**。

## 根因

小程序编译期**不做**「事件绑定名 ↔ Page 方法」的静态校验。

编译器的职责是语法和结构，事件绑定对它来说只是一个字符串属性——`bindtap="onClear"` 和 `bindtap="foobar"` 在编译阶段完全等价。要到用户真的点了那一下，运行时才去找方法，找不到就报错。

这意味着：**一个从没被点击过的按钮，可以带着这个错误上线。**

## 正确写法

没有"正确写法"，只有"保证一致"。靠人肉记是不现实的，靠 AI 自觉更不现实——它写完就往下走了。

唯一可靠的办法是**静态检查**。在每次改完 WXML 或 JS 之后跑一遍，把差集打出来。

### 仓库里配了一个能直接跑的检查脚本

[`tools/check-bindings.js`](../../tools/check-bindings.js)，零依赖，只用 Node 内置模块。

```bash
# 参数是含 app.json 的那一层目录；在你的小程序项目里跑
node /path/to/check-bindings.js ./miniprogram
```

它做的事：读出 `app.json` 里的所有页面（含分包）→ 提取每个 WXML 的 `bind*` / `catch*` 绑定名 → 提取对应 JS 里定义的方法名 → 打出差集。发现缺失就返回退出码 1，可以直接挂进提交前检查。

动态绑定（`bindtap="{{handler}}"`）会跳过，静态判断不了。

### 这个脚本的三个局限，得说清楚

1. **它用的是正则启发式，不是 AST 解析。** 方法名靠「空白 / 逗号 / 花括号之后 + 标识符 + 左括号」识别，并且只扫 `Page({` 起始位置之后的内容，避开文件上方的辅助函数。写法非常规时仍可能误报或漏报。要零误报，用 `@babel/parser` 解析出 `Page({})` 对象的顶层 key。
2. **主要面向 `Page`，不保证覆盖自定义组件。** `Component({ methods: {...} })` 结构多一层，脚本会顺带扫到，但不保证准确。
3. **结论只是提示。** 抓到问题时先打开对应 JS 确认，再决定改不改。别让 AI 拿着输出直接批量补空方法——那会造出一堆什么都不做的占位函数。

即便如此，它能抓住绝大多数漏定义——因为高频场景就是「页面里少写一个方法」，形状很固定。

### 元案例：检查工具自己也会静默失败

这个脚本的第一版要求方法定义在**行首**。遇到下面这种单行走法时，它一声不响地整片漏检：

```js
Page({ data: {}, onTap(){}, onInput(){} });
```

而 AI 生成短代码时，恰恰最常写成单行。**最该管用的场景，工具反而失效了。**

已改成不依赖行首的匹配，并用三组最小项目验证过：单行写法 / 多行含 `async` 与箭头函数 / 分包页面 + 动态绑定跳过。这件事本身就是本库主题的一个实例——**不报错的失效，连检查工具自己都不能幸免**。

## 怎么验证

除了跑脚本，还有两个手工动作值得做：

1. **新页面交付前，把每个可点元素点一遍。** 听起来很土，但漏定义的按钮恰恰是"从没被点过"的那个。
2. **看控制台的默认过滤级别。** 有些提示在默认过滤下不显示，把 Filter 设成 `Verbose` 再看一次。

## 顺带一提

同一个坑还有个变体：`bindtap` 写对了、方法也定义了，但方法里 `this` 指向不对（用了普通函数而非箭头函数，或者方法没绑定）。那个的表现是「点了报错但报的是别的错」，比这个好查，不单列条目。

## 相关的坑

- 改名重构时，除了事件绑定，`wx:if` 里引用的 data 字段、`wx:for` 里引用的数组、`url` 里的页面路径，都属于「字符串引用」，编译器同样不校验。改完一处要全局搜一遍。
